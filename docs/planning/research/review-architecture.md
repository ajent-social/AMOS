# Independent architecture review

Scope: VISION, RFC 0001, cross-lane contracts, foundation input and relevant identity/billing/platform/agent dependencies. Read-only source review; no builds, tests, provider actions or code edits. Findings below concern planning correctness, not observed implementation defects.

## Material findings

1. **S1 needs an owned shared operation runner.** `T5.9`, `T12.3` and later `T11.4` consume common policy/transaction invocation, but resolving the seam to one of these consumers would leave a hidden implementation or dependency cycle. The integrator has now identified `T2.8` as the S1 owner of `app/operation` and `app/policy`, depending on baseline identity/workspace/payment state plus jobs/audit. **Accepted correction:** wire consumers to T2.8, keep protocol adapters thin, and audit the resolved graph. Its S1 implementation must require only baseline password assurance; complete S3 proof methods remain extensions.

2. **The S2 live test-mode gate originally required S3 billing/provider work.** `T16.3` includes portal and cancellation, while the original `T5.11` depends on S3 roles and complete assurance. Broad "identity adapters complete" wording can also pull every social/MFA/enterprise provider into S2. The integrator proposes S1 `T5.22`/`T6.18` for baseline personal subscription management and narrowing T16.3 to password/email plus flat test-mode billing. **Accepted correction:** verify these tasks use recent password proof and personal billing ownership without depending on T3.17/T4.8; full methods and seat/usage qualification stay in T16.6/T16.7. Verify API and browser cancellation/portal behavior in the early slice, not merely provider helper calls.

3. **S1 synthetic setup still assumes organization creation.** `T7.6` calls for synthetic owner, organization and catalog fixtures through module APIs, although organization creation is S3 (`T4.5`). A hidden direct-SQL seed or premature full organization implementation would undermine the staged contract. **Required correction:** S1 seed only the personal workspace and flat catalog; add the organization fixture when the real organization service exists. Also freeze how the generated local app loads the explicitly development-only mail/payment adapters: T1.11 currently describes test-only injection, whereas T7.6 describes interactive local adapter modes. Make the local path reproducible and conspicuously simulated, with production activation rejected. Do not resolve this by silently enabling fixture adapters in deployed applications.

4. **The durable job guarantee overstates external fencing.** T1.10 acceptance says committed intent cannot be "executed by a stale lease holder." A database lease cannot prevent an already in-flight provider request from taking effect. This conflicts with the contracts document's correct warning against exactly-once remote execution. **Required correction:** guarantee fenced local claims/commits, stale-worker rejection and no new unapproved dispatch after observed lease loss. Preserve unknown remote outcomes and require provider idempotency/reconciliation where supported. Its failure test should lose the lease during an in-flight effect, allow the provider to accept that effect, and prove the successor does not duplicate or falsely classify the outcome.

5. **Both PostgreSQL deployment profiles are confirmed, but the RFC still disclaims that choice.** VISION and RFC section 7 correctly require managed containers/managed PostgreSQL and a small VM with PostgreSQL. RFC section 2 still says PostgreSQL was not selected, and the open-decisions text can be read as reopening the database engine. **Required correction:** retain qualification of exact managed service, driver, version, session adapter, sizing and recovery; remove wording that treats the two required PostgreSQL profiles as an unresolved product choice. Do not ask the owner to select one profile for the whole product again.

6. **Export download revocation needs a concrete contract.** T1.13 requires downloads to bind to current owner/request state; identity/workspace export tasks mention expiring download links. A direct object-store presigned URL normally bypasses a fresh application authorization check after issuance. **Required correction at T1.2/T1.13 freeze:** choose app-authorized streaming, or explicitly document and approve a bounded bearer-download lifetime/revocation limit. Test removal/disablement after link issuance and before retrieval. Do not claim immediate current-state enforcement if the chosen delivery mechanism cannot provide it.

## Confirmed boundaries and review limits

Selected authentication methods, independent personal/organization billing, all three pricing models, both integration styles, both deployment profiles, replaceable UI and automated upgrade PRs remain in scope. Identity and billing policy decisions that are genuinely open should be resolved by named freeze tasks; already confirmed product choices do not need another approval loop.

S1 can remain independent of complete S3 OAuth/MFA if the corrections above are reflected in concrete dependency IDs. Baseline primary-proof metadata and current password verification need a public seam that later assurance composes, rather than an early copy of the full enterprise/MFA stack. Selected provider fixtures, actual provider test environments, deployment and production release remain distinct evidence states.

No selected private-identifier, home-path or individual-schedule patterns were found in the reviewed VISION/RFC/contracts/foundation files. This targeted inspection is not proof of whole-repository publication safety; the explicit public-artifact gate still applies. No private implementation is needed to reproduce any finding here.
