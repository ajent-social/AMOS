# RFC 0001: AMOS application foundation and maintenance architecture

Date: 2026 09 30 UTC. Status: draft architecture incorporating confirmed product requirements. `docs/VISION.md` is the product-intent record. Implementation choices labelled proposed are not additional product decisions. This document supersedes conflicting early brainstorming proposals.

## 1. Outcome and boundaries

AMOS provides a complete owner-hosted SaaS web application, a developer CLI, public APIs, generated MCP, deployment configuration and operational tooling. It owns application identity, workspaces, policy, audit, billing and API/MCP capabilities. Developers add business functionality through a standard Go extension or separate service. One public domain serves AMOS and business routes. Independent humans and agents use the same application policy boundary. AMOS remains useful when external workflow services are unavailable.

The complete target includes personal and organization lifecycle, all selected authentication methods, MFA, OIDC enterprise federation, subscriptions in three pricing models, fully replaceable UI, operations, upgrade PRs and bounded autonomous maintenance. Delivery is staged; advertised capability must match actual evidence.

External agent runtimes and agents run independently and connect via standard MCP. External product workflow controls delivery and qualification. An external code-change lifecycle service handles PR safety and exposes executable author, independent review, bounded fix, re-review and landing tasks for normal apply-and-claim execution. Each lifecycle has one canonical scheduler and admission authority. Ordinary descendants become eligible after reviewed merge and verified landing; only explicitly speculative dependencies may start sooner, without release authority. Coding completes at PR URL and exact head handoff. Every code-changing PR receives independent exact-head review; a blocking finding creates visible bounded fix and re-review tasks. AMOS does not implement a second task/PR orchestrator. It retains owner-local diagnosis, proposal and upgrade generation, and bounded domain jobs. Maintenance release gates protect development/deployment authority and remain separate from customer-agent governance.

## 2. Distribution and runtime

Proposed module: `github.com/ajent-social/amos`; versioned Go core and CLI, default templates/assets and versioned scaffolding recipes. `amos init` generates a consumer repository with a pinned AMOS version, configuration, business package, contract, infrastructure program and GitHub Actions caller workflows. A provenance manifest records generator versions, file ownership and preimages for future upgrade diffs.

Proposed generated layout: `cmd/app`, `app/business`, `api/business.openapi.yaml`, `ui/overrides`, `infra`, `.github/workflows`, and `amos.yaml`. These are reserved seams pending the foundation freeze. Package paths inside AMOS are separately defined in the contract document and task plan. Generated transport code never overwrites business implementations.

Start with one modular Go application and PostgreSQL, selected for both deployment profiles; bounded jobs may run in the application or as separately launched workers using the same domain services. Concrete storage/session adapters and hosting components still require qualification. There is no required Kubernetes control plane, service mesh or cross-cloud runtime.

The router reserves identity/account/billing/API/MCP/health routes and explicitly registers business routes. Reject collisions at startup. Integrated handlers call domain services directly. Separate-service routes use a trusted proxy adapter: private origin, exact allowlist, bounded timeouts/body sizes, protected internal paths, streaming policy, forwarded-host handling, credential stripping and a defined authenticated identity propagation mechanism. Never trust client-supplied tenant or identity headers. The upstream must not be publicly bypassable.

## 3. Contracts and interfaces

Contract-first OpenAPI is the source for API transport, Go request/response types and MCP tool mapping. Use maintained generators/SDKs where suitable; qualify and pin exact versions. Do not implement a new MCP protocol. All exposed operations declare a stable ID, input/output schemas, actor/scopes, tenant selection, entitlement, side-effect/retry semantics and MCP exposure. OpenAPI alone is insufficient to describe these policies; a reviewed extension schema supplies them.

Domain handlers own business behavior. REST, MCP and server-rendered web entry points call that behavior through equivalent checks. Error semantics distinguish invalid input, unauthenticated, forbidden, conflict, not found and dependency unavailable. Define non-enumerating responses at sensitive identity boundaries. Mutations need idempotency or explicit non-retry behavior. Unknown outcomes remain observable rather than becoming success or denial by accident.

All applicable AMOS and business operations are available to agents. Protocol access does not bypass step-up authentication, identity proof, ownership or billing authority. Operations requiring human proof return a resumable challenge; they are not implemented as an agent bypass or silently labelled UI-only. API keys cannot grant new authority to themselves. Public discovery, registration and authorization endpoints have separate resource bounds.

## 4. Identity, tenancy and authorization

Keep installation, application, environment, person, external identity, workspace and membership distinct. Each person receives a personal workspace and can join organizations. Tenant selection is explicit and verified against current membership. Email equality never links identities without proof. Business resources retain owner/tenant checks at the resource boundary.

Selected methods: password, magic link, Google, GitHub, Apple, passkey and per-organization OIDC SSO. Identity linking/unlinking, verification, profile changes, recovery, session inventory/revocation, disablement, export/deletion and tenant ownership transfer require designed lifecycle behavior. Prevent last-owner removal and loss of the final viable sign-in method. Credentials, sessions and grants respect account/organization/membership disablement with documented consistency bounds.

MFA includes enrollment, challenge, recovery, rotation and organization enforcement. Proposed first methods are TOTP and qualified passkey assurance, with recovery codes and a separately reviewed recovery process; exact provider assurance and step-up semantics must be frozen before implementation. No invented account-recovery bypass. Enterprise SSO domain verification, tenant binding and IdP configuration must not establish authority merely from an email domain.

Proposed roles are owner/admin/member plus application-defined permissions. AMOS supplies evaluation and membership; the app supplies its permission vocabulary and resource semantics. Protect session cookies, CSRF, redirect allowlists, rate limits and credential storage using qualified established mechanisms.

Customer API keys have one-time secret display, hashed verification, explicit owner/tenant/resource/scope bindings, expiry, revocation and rotation. MCP OAuth is per registered resource and identity boundary, with grant lifecycle and current membership checks. Supported protocol/client versions are qualified, not inferred from package existence.

## 5. Billing

Each personal workspace and organization has independent billing ownership. Stripe is required initially through a provider adapter; future provider differences remain explicit rather than hidden behind universal success assumptions. Plan catalog supports flat recurring monthly/yearly, seat quantities and usage meters. Define whether they may combine, seat counting, proration, periods, trial/grace, cancellation, refunds, disputes, tax responsibility and plan changes in a policy freeze.

Provider operations use durable intent, bounded retries and provider-supported idempotency. Signature verification uses the provider SDK. Webhook receipt is durable before acknowledgement; duplicate/out-of-order events and missed events converge through reconciliation. Provider confirmation, not a redirect, enables paid access. Keep allowed, denied and unavailable distinct with freshness metadata. Account/recovery/billing access survives loss of paid access.

Usage needs attributable immutable event identity, deduplication, period boundaries, corrections and reconciliation; the AMSL bounded usage counter is not itself a financial ledger or invoice engine. Tenant authorization remains mandatory even when billing says allowed. Concurrent membership/seat changes and uncertain payment outcomes require explicit tests.

## 6. UI and upgrade ownership

Default server-rendered Go/HTMX pages are production implementations with accessibility, responsive behavior and plain-text escaping. Business landing/pages belong to the developer. Themes, individual template overrides and a completely custom UI are supported through documented contracts. No frontend authority supersedes the backend.

The core, default UI and scaffolding recipes have explicit compatibility versions. Release and upgrade profiles are immutable, versioned inputs. Upgrades pin immutable releases. `amos upgrade plan` proposes dependency/configuration/generated-file/migration changes; apply produces a reviewable local change. Generated infrastructure/workflows retain a managed ownership manifest, a three-way comparison and a conflict stop. Never overwrite customized files based only on a generated-path name. Do not transplant restricted implementation source into this public repository.

Automated upgrade PRs are required. They include compatibility notes, impacted overrides, checks and recovery guidance. Custom pages declare the UI contract they target. New security or functional requirements that cannot be mechanically adopted produce actionable incompatibility instead of a false successful upgrade.

Use expand/contract data migrations where practical; destructive schema cleanup is a separate gated event. Rollback may mean a forward repair or data restore rather than just running the old binary. Protect identity epochs so restoring a backup cannot silently resurrect revoked credentials.

## 7. Infrastructure and operations

AWS first, Cloudflare required. Two selected deployment profiles are required: managed containers with managed PostgreSQL, and a smaller virtual machine hosting the app and PostgreSQL. Choose per installation during initialization. ECS/Fargate plus RDS and EC2 plus Podman are proposed concrete implementations to qualify. Each profile has its own availability, maintenance, cost, backup and recovery evidence. Changing profiles is an explicit data/infrastructure migration, never an automatic configuration toggle. Cloudflare DNS-only and reverse-proxy behavior are different contracts; current AMSL DNS alias rejects proxied records. Required Cloudflare does not silently mean WAF/proxy features were approved.

Use Pulumi Go with an owner-controlled state backend as the planning default. Bootstrap state, locking, encryption, import/adoption, secrets and destructive changes need explicit procedures. Deploy identity uses short-lived federated credentials scoped to repository/environment/resources. Initial account, DNS ownership, certificates, GitHub repository configuration, email and payment setup are tracked external gates.

Provide local execution, credential-free fixtures, health/readiness, structured redacted logs, bounded metrics/traces, crash reporting, alerts, backups, restore drills, migration jobs and release recovery. Provider mocks, previews, disposable cloud checks and production verification are separate evidence classes. Production changes require scoped authorization and budget even if local tests pass.

An installation retains useful application service during loss of upstream reporting, upgrade automation or maintenance agents. Define telemetry volume, retention, redaction and cost bounds. Database recovery, file/object recovery and deployment rollback are distinct capabilities.

## 8. Self-improvement

Two policy domains: owner-account maintenance for private application code/custom UI/infrastructure, and independent AMOS upstream maintenance for shared code. AMOS provides owner-local diagnosis, proposal/upgrade generation and bounded domain jobs; it does not schedule a second task/PR lifecycle. Code changes use the code-change lifecycle service's canonical executable author/review/fix/re-review/landing tasks, and product delivery/qualification stays with the product workflow controller. Logs and crash data may inform local diagnosis; upstream export uses a strict allowlist of sanitized diagnostics and excludes raw logs, business data, secrets and identifying infrastructure details. Redaction alone is not proof of safety: structured schemas, bounded payloads, rejection tests and owner controls are required. Provide inspection, disablement and retention settings.

Sequence: observe -> classify -> deduplicate -> evidence bundle -> bounded task -> isolated agent workspace -> independent verification -> policy decision -> immutable artifact -> staged rollout -> health evaluation -> promote or recover. The chosen model/runtime is accessed through an adapter, with owner credentials, spend/time limits, egress constraints and explicit failure states. Telemetry and repository text are untrusted input, not executable instructions.

Coding jobs lack production credentials and cannot alter mandatory acceptance controls, policy, protected workflow gates or their own release permissions. An independent verifier tests the proposed behavior and critical denied paths. A separate release identity evaluates exact source/artifact attestations and owner policy. Promotion atomically checks the expected installed release generation; stale approvals cannot deploy over a newer accepted release. Eligible low-risk fixes may proceed automatically through release and deployment; sensitive identity/billing/security-policy changes, destructive migrations and uncertain recovery require explicit elevated review under proposed defaults.

Private fixes stay private. Upstream reports or reproductions are publishable synthetic evidence; suspected vulnerabilities use a private disclosure path rather than automatic public issues. Scope and severity classification itself is validated and bounded. Upstream release produces consumer upgrade PRs; owner policies determine autonomous adoption. Code-changing PRs require independent exact-head review, and ordinary dependent work waits for reviewed merge and verified landing. Product qualification remains a separate gate; landed code alone does not establish provider or production readiness. Canary failure, budget exhaustion, repeated failing attempts or unknown state halt automation and retain diagnostics. Manual kill switch and credential revocation remain available independently of the agent.

## 9. AMSL reuse and contribution boundary

AMSL is the preferred candidate foundation where qualified: `servicecred`, `mcpoauth`, selected account/auth components, checkout/subscription/provider adapters, Pulumi security components and reusable delivery workflows. Inventory immutable revisions and local dirt before use. The catalog remains the authority on maturity. Current documentation calls implementations candidates, not stable qualified platform services.

AMSL owns reusable mechanisms and their guarantees; AMOS owns lifecycle composition, workspace policy, UI, pricing/entitlements, app routing and maintenance orchestration. AMSL `tenant` is instance provisioning, not organizations; `sealedvault` stores caller-sealed data, not KMS; password reset is not password authentication; usage counters are not financial metering. Do not rebrand these gaps as working features.

For a concrete gap: create a failing consumer case -> check standard library/mature alternatives -> choose local composition or narrowly scoped upstream change -> test compatibility and denied behavior -> maintainer review/release -> pin in AMOS -> repeat composed checks -> update honest public evidence. Keep catalog maturity promotion separate from an AMOS release. AMOS automatic maintenance authority does not override AMSL's human-review requirements for security-sensitive APIs.

Do not copy restricted source material into public repositories absent provenance/publication qualification. Existing implementations must be qualified at their actual revision. Public evidence must be independently reproducible; restricted observations are not public adoption evidence.

## 10. Delivery and acceptance

Stages: foundation/contracts; local new paid-app slice; qualified AWS/Cloudflare deployment; complete selected identity/teams/billing; full API/MCP and custom UI compatibility; upgrade PRs and operating drills; owner-controlled and upstream autonomous maintenance. Some independent work can overlap after contracts freeze; the plan defines dependencies and ownership rather than assuming sixteen agents make all work independent.

The first reference milestone has a distinct rehearsal gate. Prefer a small working reference business feature, one qualified sign-in method, personal workspace, one recurring test-mode plan, protected domain action and a deploy/recovery path. This is a staged subset, not removal of the complete scope. Live payment acceptance and provider onboarding are separate from fixture-based demonstration.

Every stage has observable API/browser/negative-path evidence. Document not-run provider checks and external blockers. No simulated provider response in production. Coding task completion, merged integration, deployed release and workshop rehearsal have separate status fields.

## 11. Open decisions and adoption gate

Freeze the proposed storage/session/compute/email/toolchain/MCP profile, domain example, license and cost policy through named tasks. Determine OIDC/MFA assurance, subscription combinations and billing policy before irreversible data contracts. Open choices have proposed defaults and explicit blockers; lower-reasoning workers must not improvise cross-cutting architecture.

The accompanying plan records exact use cases, task contracts, staged gates, AMSL upstream work, shared-file ownership, up to sixteen execution lanes, and an audit for requirement coverage and unresolved dependencies. This RFC is the reference design for that plan, not approval to provision, publish or spend.
