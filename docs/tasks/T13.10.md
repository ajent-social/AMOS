# T13.10: Separate release identity and idempotent artifact promotion

Status: PLANNED. Execution evidence is recorded below; release acceptance remains separate. Stage S5; wave 42; owning lane L15; estimate 90 minutes (planning hypothesis).

## Objective

Make actual deploy authority inaccessible to coding and verification jobs.

## Dependencies and readiness

T13.9, T7.11, T9.5

Read the actual outputs of every dependency before starting. Reconcile this contract against the frozen contract version and current code; report material mismatch instead of inventing behavior. The listed verification commands are future prescriptions, not claims that executables already exist.

External gate: None beyond normal task authorization and prerequisites.

## Scope

- internal/maintenancerelease/*
- infra/fragments/maintenance-release-role.*

Only these owned paths may change. Repository-qualified upstream paths require a separate upstream task claim and that repository's permissions/review rules; they are not permission to edit a neighboring checkout. Shared module files, migration ordering, aggregate APIs, root workflow wiring and executable entrypoints remain integrator-owned unless explicitly listed and exclusively delegated.

## Implementation instructions

1. Implement a release adapter accepting only signed policy decisions and exact immutable artifact/target references.
2. Exchange narrowly scoped short-lived deployment credentials under independently protected identity trust.
3. Persist promotion request/result IDs and reconcile unknown provider outcomes before retry; never deploy by mutable tag.
4. Test coding-role denial, substituted digest, duplicate delivery and credential expiration before/after provider acknowledgment.
5. Bind release authorization to the expected currently installed release/generation and atomically compare-and-swap that generation before promotion; stale approvals require replan/reverification, including across independent repair jobs.

## Acceptance criteria

- Coding and verifier identities cannot acquire the release role or call promotion successfully.
- Repeated same request deploys at most once; unknown results remain reconciled/held.
- Scoped checks, formatting and configured lint pass; E16 separately records any required deployed/live verification before this behavior is advertised.
- Two independently approved jobs racing on one installation cannot deploy out of order: after one changes the generation, the other stale job is rejected.
- Immediately before promotion, current owner policy/pause and installed release/schema generation still match the authorized evidence; unknown or stale state stops.

Use cases: UC-100, UC-101, UC-115.

## Negative verification

Crash between provider deploy acceptance and local receipt commit; recovery queries the same operation and does not promote twice.

For behavior changes, show the check detects the predicted failure using a disposable isolated test mutation, then restore and report the passing check. Never damage a shared checkout or live environment. A design-only task uses a rejected schema/document fixture instead of pretending it changes runtime behavior.
