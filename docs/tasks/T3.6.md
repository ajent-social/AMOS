## Implementation instructions

1. Implement verification issue/confirm using qualified token primitives; persist hashed challenges and transactional email intents.
2. Bind purpose, person, proposed email and expiry; consuming GET links renders confirmation rather than mutating proof to tolerate link scanners.
3. Retry delivery with bounded attempts and safe templates; redact challenge values and expose generic request acknowledgement.
4. Test expired/replayed/wrong-purpose verification and rollback when outbox creation fails through real API.
5. Format touched Go files with gofmt and changed frontend files with the pinned formatter; run scoped vet/lint and the named behavioral checks, rejecting skipped or zero matching tests.

## Acceptance criteria

- Confirmation consumes exactly one challenge and verifies only its bound email.
- Provider failure leaves a retryable delivery intent and does not silently verify ownership.

Use cases: UC-020, UC-022, UC-029.
