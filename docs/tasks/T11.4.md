# T11.4: Adapt standard SDK calls to domain invocations

Status: PLANNED. Detailed draft, not execution-certified. Stage S3; wave 15; owning lane L14; estimate 60 minutes (planning hypothesis).

## Objective

Use the qualified SDK as transport and invoke the same application services as REST.

## Dependencies and readiness

## Implementation instructions

1. Register generated descriptors through the official SDK and inject authenticated principal/resource/workspace context.
2. Dispatch into shared domain invocation; preserve validation, entitlement, authorization and safe error taxonomy.
3. Bound request size, deadlines, response size and cancellation; return structured uncertainty for interrupted mutations.
4. Add real HTTP MCP initialize/list/call tests asserting response bodies and denied calls.

## Acceptance criteria

- Actual MCP calls reach the same service spy/transaction effects as equivalent REST calls.
- Unauthenticated, wrong-workspace and unsubscribed calls cannot invoke the domain mutation.
- Scoped checks, formatting and configured lint pass; E16 separately records any required deployed/live verification before this behavior is advertised.

Use cases: UC-080, UC-081, UC-087.

## Negative verification

Send a correct tool name with a forged workspace argument; no unauthorized domain invocation occurs.

For behavior changes, show the check detects the predicted failure using a disposable isolated test mutation, then restore and report the passing check. Never damage a shared checkout or live environment. A design-only task uses a rejected schema/document fixture instead of pretending it changes runtime behavior.
