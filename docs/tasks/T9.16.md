# T9.16: Exercise upgrade lifecycle against generated applications

Status: PLANNED. Detailed draft, not execution-certified. Stage S4; wave 20; owning lane L12; estimate 90 minutes (planning hypothesis).

## Objective

Verify upgrades preserve application behavior and owner modifications.

## Dependencies and readiness

T9.11, T9.12, T9.13, T9.15, T1.5

Read the actual outputs of every dependency before starting. Reconcile this contract against the frozen contract version and current code; report material mismatch instead of inventing behavior. The listed verification commands are future prescriptions, not claims that executables already exist.

External gate: None beyond normal task authorization and prerequisites.

## Scope

- tests/upgrade/lifecycle_test.go
- tests/upgrade/testdata/*

Only these owned paths may change. Repository-qualified upstream paths require a separate upstream task claim and that repository's permissions/review rules; they are not permission to edit a neighboring checkout. Shared module files, migration ordering, aggregate APIs, root workflow wiring and executable entrypoints remain integrator-owned unless explicitly listed and exclusively delegated.

## Implementation instructions

1. Generate a prior-version app, add synthetic business code and supported overrides, then upgrade to the current fixture version.
2. Run real module tests, migration checks and scripts/test-browser.sh upgrade from T1.5 against the upgraded tree.
3. Test failed merge, removed module, rollback incompatibility and repeated upgrade.
4. Assert business files and secrets remain byte-identical and produce a reviewable diff.
5. Implement the named verification cases at the real changed boundary; run the specified negative case in a disposable fixture, observe its predicted failure, restore the behavior, and record both results.

## Acceptance criteria

- Successful upgrade preserves tested business behavior and customizations.
- Conflicted upgrade leaves original app runnable and unchanged.
- Named scoped checks pass and the specified negative case is demonstrated; live/production qualification remains a separate explicitly authorized E16 gate where applicable.

Use cases: UC-068, UC-069, UC-070, UC-071.

## Negative verification

Delete an owner-authored handler during the fixture upgrade and observe preservation assertions fail.

For behavior changes, show the check detects the predicted failure using a disposable isolated test mutation, then restore and report the passing check. Never damage a shared checkout or live environment. A design-only task uses a rejected schema/document fixture instead of pretending it changes runtime behavior.
